\subsubsection{boot-update}
\label{sec:org97d8672}
grubの設定を助けてくれるツールのようだ。\href{http://www.funtoo.org/en/funtoo/core/boot/}{boot-update} というもので、grub-1.97+を試してみたけれど、multiboot にはまだきちんと対応していないみたい。/etc/boot.conf に次のように書いておいて `boot-update` と打つだけで済むので楽ではあるものの、"Backtrack 4" のほうは利用側の root-fs が無理やり埋め込まれてしまっているので、少し手直しが必要になる。/boot/grub/grub.cfg を手で修正すれば大丈夫。

\begin{verbatim}
boot {
    path /boot
    generate grub
    default "Funtoo Linux"
    timeout 3
}

"Funtoo Linux" {
    kernel /kernel-genkernel-x86[-v]
    initrd initramfs-genkernel-x86[-v]
    params += crypt_root=/dev/sdc2 root_keydev=/dev/sde1 root_key=/keyfile

\subsection{{\bfseries\sffamily DONE} このサイトのデプロイについて}
\label{sec:org0bbad39}
世の中にはたくさんのブログサービスがあって、そのお手軽さもそれはそれで魅力的だけど、静的サイトジェネレータには静的サイトジェネレータならではの良さがある。動的サイトのようにレンダリング処理が要らないぶん、表示が速いのもポイント。メモ帳程度の文章をつらつら書くだけなので、あまり凝る必要もない。そんな理由から静的サイトジェネレータを選んでいる。

ドメインは自分で取得したものだけど、サイト自体はあちこち渡り歩いてきた。いまは GitHub Pages を使っている。これまでは作ったコンテンツをローカルの\href{https://github.com/ac1965/ac1965.github.io}{GitHub Pages}のリポジトリに \texttt{rsync} してから \texttt{git push} していたのだけど、それすら面倒に感じるくらいのオッさんになってきたので、Post を作って \texttt{git push} したら自動でデプロイされる方向に切り替えたいと思い始めた。

以下、git アカウントの作成や Hugo サイトの構築、git まわりの設定はすでに済んでいる前提で進める。
\subsubsection{GitHub Pagesでデプロイ}
\label{sec:orgc1d3998}
\begin{itemize}
\item \href{https://docs.github.com/ja/pages/getting-started-with-github-pages/about-github-pages}{GitHub Pages について}
\item \href{https://pages.github.com}{GitHub Pages}
\item \href{https://github.com/actions/deploy-pages}{deploy-page}
\end{itemize}

これによると、 \textbf{GitHub Pages} には2つのタイプがあるらしい。

\begin{itemize}
\item User or Organization Site
\texttt{https://<username or organization>.github.io/} のURLで公開されるタイプ
\item Project Site
\texttt{https://<username>.github.io/repository/} のURLで公開されるタイプ
\end{itemize}

リポジトリ名が \texttt{username.github.io} 以外の場合は後者になるということがわかった。たぶん、その理解で合っていると思う。

つまり \url{https://gohugo.io/hosting-and-deployment/hosting-on-github/} のやり方をそのままやると、\url{https://www.ty07.net/hugo-mysite/} のようなURLで公開されてしまう。期待どおり \url{https://www.ty07.net} のURLで公開しようとすると、結局 \href{https://github.com/ac1965/ac1965.github.io}{GitHub Pages} のリポジトリに \texttt{rsync} してから \texttt{git push} する方法しかないのだろうか😓
\subsubsection{すこしたった後に思ったこと。}
\label{sec:orgc3dadf9}

\href{https://github.com/peaceiris/actions-hugo}{actions-hugo} を先に読んでいれば、もう少し理解が早かったかもしれない。要するに \texttt{https://<username>.github.io/} 側に Hugo の環境を入れて、GitHub Pages にデプロイすればいいということがわかった。

\label{sec:org61a945c}

\subsubsection{そもそもなぜこんな構成にしたのか}
\label{sec:org3c0c881}

Emacs の設定は、放っておくと本当にカオスになってしまう。 \texttt{init.el} に \texttt{setq} がだらだらと並んで、どれが何のためにあるのか誰にもわからなくなる（かくいう自分も含めて）。

そこで数年前に、思い切って全部作り直した。コンセプトはシンプルで、

\begin{itemize}
\item 設定をきちんとエンジニアリングの成果物として扱うこと
\item どのモジュールを消しても他が壊れないこと
\item どの環境で起動しても同じ結果になること
\end{itemize}

この3つを最初から保証できる構成にしている。
\subsubsection{Literate Configuration}
\label{sec:org1f592c9}

\texttt{README.org} が唯一の真実の源泉になっている。Emacs Lisp のコードはすべて \texttt{README.org} 内の \texttt{src} ブロックに書いておき、 \texttt{org-babel-tangle} で \texttt{lisp/<layer>/<module>.el} に書き出す仕組みだ。

保存時に自動でタングルされるようにしてあるので、実際の作業フローはほぼ「 \texttt{README.org} を編集して保存するだけ」になっている。

ドキュメントとコードが同じファイルにあるので、「コードはあるけど意図がわからない」という状況が生まれない。これがいちばんの利点だと思っている。
\subsubsection{階層アーキテクチャ}
\label{sec:org0b8a656}

設定は10層に分かれていて、依存関係は必ず下から上への一方向のみ。

\begin{verbatim}
early-init → core → ui → auth → completion → orgx → vcs → dev → utils → personal
\end{verbatim}

\texttt{core} が UI に依存してはいけないし、 \texttt{vcs} が \texttt{dev} に依存してもいけない。この制約を守ることで、モジュールを消したり差し替えたりしても他が壊れないようにしている。

起動時のオーケストレーションは \texttt{modules.el} が担っていて、モジュールごとにエラートラップをかけながらロードしていく。 \texttt{my:modules-verbose} を有効にすると、モジュールごとの起動時間も表示されるので、何が遅いのかも一目でわかる。

\label{sec:org4a96cd8}

今月は、わりと大きめの追加が4つあった。
\begin{enumerate}
\item Claude API クライアントを \texttt{utils} 層に追加（Fix AL）
\label{sec:orgbedaa02}

\texttt{utils/utils-claude.el} として、低レベルの HTTP クライアントを作った。公開しているAPIは3つの関数だけ。

\begin{center}
\begin{tabular}{ll}

\end{verbatim}

これを \texttt{C-c C-c} で評価すると、そのままアシスタントの応答が結果として入る。 \texttt{:system} ・ \texttt{:model} ・ \texttt{:tokens} といったヘッダ引数もサポートしている。

\item 保存時に自動で ox-hugo エクスポート（Fix AO）
\label{sec:org9ed0bca}

\subsection{{\bfseries\sffamily DONE} このブログについて}
\label{sec:org3886a54}
最初はHTMLを手書きしていた。テキストエディタでタグを打って、FTPでアップして、というやつ。今思えばよくやっていたなと思うけど、当時はそれが当たり前だったし、むしろ楽しかった気もする。 \texttt{<html>} とか \texttt{<table>} とか、ちまちまタグを書きながら「これでちゃんと表示されるかな」とブラウザでリロードする、あの感じ。デザインも全部手作りで、我ながら素朴なものだったけど、自分で作った実感があってよかった。

その後、ブログエンジンをいくつか渡り歩いた。PyBlosxom を使っていた時期もあって、Python で書かれた軽量なやつ。テーマやプラグインを自分でいじれるのが気に入っていた。コメント欄のスパム対策や、シンタックスハイライトの設定など、今となってはどうでもいいような細部に妙に時間をかけていた記憶がある。そこからいろいろあって、今は Hugo に落ち着いている。静的サイトジェネレーターなので速いし、Emacs との相性も悪くない。

書いていることは昔から一貫していて、要は「自分が触っているもの」の記録。2009年ごろは Gentoo Linux で Live CD を作っていたり、awesome → xmonad とウィンドウマネージャを渡り歩いていたり。当時の自分は、わりとやんちゃだったなと思う。Guruplug とか EeePC とか、懐かしい単語が記事に並んでいる。あの頃は「小さくて低消費電力の Linux マシン」のようなものに、妙にテンションが上がっていた。今でいう Raspberry Pi みたいな感覚だったのかもしれない。

昔の記事は全部残っているわけではない。手書きHTMLの頃のものは断片的にしか残っておらず、残っているものから起こしている状態。ちゃんとバックアップしておけばよかったとは思うけれど、まあ、それでもいいかなとも思っている。完璧なアーカイブではなく、残っていたものが残っている、くらいの温度感で。むしろ抜けている部分があるからこそ、「あの時期はそういう感じだったんだろうな」と想像する余地があって、それはそれでいい気がしている。

更新頻度は正直低い。気が向いたときや、まとめたいことができたとき、そのくらい。日記代わりにせっせと書くつもりはないし、PV稼ぎにもそれほど興味はない。書きたいから書く、それだけ。下手に「週1更新」なんて決めてしまうと途端につらくなるのが目に見えているので、最初からそういうルールは作っていない。

最近は Emacs の設定まわりや、AI / LLM 関連の話題が多くなってきた。興味が生成AI絡みのことに向くようになってきたので、自然とそちらに引っ張られている感じ。技術トレンドは移り変わりが速いので、自分の中で整理する意味でも、こうして書いておくのは悪くないと思っている。書きながら考えがまとまることも、わりとある。

ちなみに今のワークフローは、Emacs の Org-mode でざっくり書いて、ox-hugo で変換して Hugo でビルドする構成。保存すれば自動でエクスポートされるようになったので、だいぶ楽になった。以前は「書く気はあるのに、投稿するまでの手順が面倒」ということがあったけれど、今はそのあたりのフリクションがほとんどなくなっている。

細々とでも続いているのは、自分のためのメモとして機能しているからだと思う。数年前に書いた設定を見返して「あー、こんなことをやっていたな」となるのが、意外と悪くない。誰かの役に立てばそれはそれで嬉しいけれど、まずは自分のための場所として、これからものんびり続けていくつもり。
\subsection{{\bfseries\sffamily DONE} Claude on Safari}
\label{sec:org96b0a71}
macOS デスクトップアプリ版の Claude で、たまにチャット入力欄がフリーズすることがある。特にシークレットチャットで固まると、履歴が残らないぶん地味に悲しい。

ブラウザ版ならリロードすれば復帰できるので助かるのだが、今度は Safari 特有の別の問題にぶつかった。日本語入力で変換を確定するために押した Enter キーが、そのままメッセージ送信として扱われてしまうのだ。これはこれでストレスが溜まる。
\subsubsection{原因：ブラウザは「確定のEnter」と「送信のEnter」を区別できない}
\label{sec:orga8b3c6c}

調べてみると、原因はブラウザの仕組みにあるらしい。

日本語IMEを使っているとき、変換候補を確定するための「確定Enter」と、メッセージを送るための「送信Enter」は、ブラウザ側からはどちらも単なる \texttt{event.key === 'Enter'} にしか見えない。本来なら \texttt{compositionstart} / \texttt{compositionend} イベントを使って「いま入力中かどうか」を判定すべきところだが、Safari はこのイベントの取りこぼしが Chrome より目立つらしく、確定した直後の Enter がそのまま送信として伝わってしまう。
\subsubsection{対策：Userscripts でこのサイトだけピンポイントに直す}
\label{sec:org0a7689b}

対処法をいくつか検討したが、直したいのは claude.ai だけなので、Safari 拡張機能の Userscripts（開発者：Justin Wasack）でピンポイントに対応することにした。Mac App Store から無料でインストールできるのも決め手のひとつ。

手順は次のとおり。Userscripts をインストールしたら Safari の拡張機能から有効化し、ツールバーのアイコンをクリックして出てくる画面から進める。

貼り付けるコードはこちら。

\begin{verbatim}
// ==UserScript==
// @name         Claude.ai IME Enter Fix (Safari)
// @namespace    local
// @version      1.0
// @match        https://claude.ai/*
// @run-at       document-start
// @grant        none
// ==/UserScript==
(function () {
  'use strict';
  let isComposing = false;
  let lastCompositionEndTime = 0;
  const THRESHOLD_MS = 300;

  document.addEventListener('compositionstart', () => {
    isComposing = true;
  }, true);

  document.addEventListener('compositionend', () => {
    isComposing = false;
    lastCompositionEndTime = Date.now();
  }, true);

  document.addEventListener('keydown', (event) => {
    if (event.key === 'Enter' && !event.shiftKey) {
      const withinGuard = isComposing ||
        (Date.now() - lastCompositionEndTime < THRESHOLD_MS);
      if (withinGuard) {
        event.stopImmediatePropagation();
        event.preventDefault();
      }
    }
  }, true);
})();
\end{verbatim}

保存できたら、実際にちゃんと動くか試してみよう。

これで問題なければ、日本語入力中の誤送信フラストレーションからは解放されるはず :-)

\subsubsection{捨てられるもの、その1：tree-sitter まわりの自作コード}
\label{sec:orgce1dca2}

\subsubsection{これまでの苦労}
\label{sec:org5a24a26}

tree-sitter は、プログラムの構造を正確に解析して色分け（シンタックスハイライト）や
インデントを賢くしてくれる仕組みだ。Emacs 29 から使えるようになった。

ただ、これまでは使い始めるまでが面倒だった。

\begin{enumerate}
\item 言語ごとに「文法定義（grammar）」を自分でダウンロード・コンパイルする
\item \texttt{python-mode} を \texttt{python-ts-mode} に読み替える設定を書く
\item 起動時に文法定義が揃っているか確認する
\end{enumerate}

この3つを自動化するために、私は 155 行ほどのコードを書いていた。
\texttt{core-treesit.el} というファイルだ。
\subsubsection{Emacs 31 での変化}
\label{sec:org84e443e}

31 では、この3つが \textbf{ほぼ全部、本体の機能になった} 。

\begin{itemize}
\item \texttt{treesit-enabled-modes} を \texttt{t} にすると、
「文法定義があるモードは自動的に ts-mode 版を使う」ようになる。
モードの読み替え表を自分で書く必要がなくなった。
\item \texttt{treesit-auto-install-grammar} を設定すると、
文法定義がないときに「入れますか？」と聞いて自動導入してくれる。
起動時の一括インストール処理も要らなくなった。
\end{itemize}

結果、155 行あったファイルは \textbf{55 行程度まで縮んだ} 。
残ったのは「どの言語の文法定義をどこから取ってくるか」という一覧表だけである。

\begin{verbatim}
(leaf treesit
  :straight nil
  :if (and (fboundp 'treesit-available-p) (treesit-available-p))
  :custom
  ;; 文法定義がある ts-mode はすべて有効化する
  ((treesit-enabled-modes        . t)
   ;; 文法定義がなければ、確認のうえ自動インストールする
   (treesit-auto-install-grammar . ask)
   (treesit-font-lock-level      . 4)))
\end{verbatim}

たった数行。100 行が消えた。
\subsubsection{ひとつ落とし穴がある}
\label{sec:org62ce095}

\texttt{treesit-enabled-modes} が面倒を見てくれるのは、
\textbf{Emacs に組み込まれている ts-mode だけ} だ。

サードパーティ製のモード（ \texttt{json-mode} や \texttt{toml-mode} など）からの読み替えは対象外なので、
そのままだと期待どおりに動かない。

これは「困った問題」ではなく、むしろ整理のチャンスだと考えている。
\texttt{json-ts-mode} や \texttt{toml-ts-mode} は Emacs 本体に入っているのだから、
サードパーティのパッケージのほうを消してしまえばいい。
パッケージが2つ減る。
\subsubsection{捨てられるもの、その2：「保存時に行末の空白を消す」設定}
\label{sec:org07fe3cd}

これは Emacs 使いなら誰もが一度は書く設定だと思う。

\begin{verbatim}
;; 昔の書き方
(add-hook 'before-save-hook #'delete-trailing-whitespace)
\end{verbatim}

「ファイルを保存するとき、行末の余計な空白を自動的に消す」というものだ。
自分のコードをきれいに保つには良い設定である。
\subsubsection{ただし、これは事故のもとでもある}
\label{sec:orgc9af5e4}

問題は、この設定が \textbf{開いたファイルすべてに効いてしまう} ことだ。

他人が管理しているリポジトリのファイルを、ちょっと確認するために開いて、
うっかり \texttt{C-x C-s} を押したとする。
すると、行末の空白がある全部の行が「変更あり」と判定されてしまう。

たった1文字直すつもりが、200 行の差分が出る。
プルリクエストを送る前に気づけばいいが、気づかないこともある。
これは典型的な事故パターンだ。
\subsubsection{Emacs 31 での解決}
\label{sec:org28aa548}

31 は \texttt{delete-trailing-whitespace-mode} という新しいマイナーモードを用意した。
「全ファイルに効くフック」ではなく、
「そのバッファだけに効くモード」として空白削除を有効にできる。

\begin{verbatim}
(leaf files
  :straight nil
  :custom ((require-final-newline . t)
           (delete-trailing-lines . t))
  ;; プログラム・Org・設定ファイルのときだけ有効にする
  :hook ((prog-mode-hook . delete-trailing-whitespace-mode)
         (org-mode-hook  . delete-trailing-whitespace-mode)
         (conf-mode-hook . delete-trailing-whitespace-mode)))
\end{verbatim}

効く範囲を自分で決められる。これが本来あるべき形だと思う。
\subsubsection{捨てられるもの、その3：「定期的に保存する」ための自作タイマー}
\label{sec:org2904f40}

Emacs には、最近開いたファイル（ \texttt{recentf} ）や、
ファイル内の最後のカーソル位置（ \texttt{saveplace} ）を記録してくれる機能がある。

ところがこれらは、標準では \textbf{Emacs を終了するときにしか保存されない} 。
Emacs がクラッシュしたり、強制終了したりすると、記録が失われる。

そこで多くの人が、こういうコードを書く。

\begin{verbatim}
;; 5分ごとに保存する自作タイマー
(run-with-timer 300 300 #'recentf-save-list)
\end{verbatim}

Emacs 31 は、これを設定項目として用意した。

\begin{verbatim}
(leaf recentf :straight nil
  :custom ((recentf-autosave-interval . 300)))   ; 300秒ごとに自動保存

(leaf saveplace :straight nil
  :custom ((save-place-autosave-interval . 300)))
\end{verbatim}

\textbf{ここで大事な注意点がひとつある。}

これらの設定は「値をセットする」だけでなく、
「タイマーを仕掛ける」という副作用を持っている。
そのため、 \texttt{setq} で書いても \textbf{効かない} 。必ず \texttt{setopt} （leaf なら \texttt{:custom} ）を使うこと。
これは NEWS でもはっきり警告されている。
\subsubsection{捨てられるもの、その4：連打を抑える処理}
\label{sec:org8f2a229}

私の設定には \texttt{orgx} という Org 拡張のレイヤーがあって、
そこで「保存のたびに重い処理が走らないように間引く」コードを3か所書いていた。

たとえば私の設定は README.org という 13,826 行のファイル1本から生成されている。
このファイルを保存するたびに、全体を解析して各設定ファイルを吐き出す（tangle する）。
連続して \texttt{C-x C-s} を押すと、そのたびに 13,826 行の処理が走る。重い。

そこで「最後の保存から2秒経つまで待つ」という制御を自分で書いていた。
プログラミングの世界では「デバウンス」「スロットル」と呼ばれる、よくあるパターンだ。

Emacs 31 は \texttt{timeout.el} というライブラリを標準で同梱するようになった。

\begin{verbatim}
(require 'timeout nil t)

;; 「2秒に1回まで」に制限する
(timeout-throttle #'orgx-auto-tangle--tangle 2.0)
\end{verbatim}

1行である。

ただし、これで自作コードを全部消していいわけではない。
\texttt{timeout-throttle} は「呼び出し頻度を制限する」だけで、
「すでに走っている処理に二重で入ってくるのを防ぐ」わけではない。
再入防止のフラグは \textbf{残しておくべき} だ。

こういう「本体機能で置き換えられる範囲と、そうでない範囲」を見極めるのが、
リファクタリングでいちばん頭を使うところである。
\subsubsection{ここからは「増やす」話：Emacs 31 の新機能で嬉しかったもの}
\label{sec:org8d36dad}

捨てる話ばかりしてきたが、31 には積極的に取り入れたい新機能も多い。
特に印象的だったものを挙げる。
\subsubsection{Git 操作が本体だけでかなり戦えるようになった}
\label{sec:orgc577f8b}

Emacs で Git を使うなら Magit、というのがここ10年の常識だった。
Emacs 標準の VC は、正直そこまで便利ではなかったからだ。

ところが 31 の NEWS を読むと、VC 関連の変更項目が \textbf{40 を超えている} 。

\begin{itemize}
\item 複数 worktree の操作
\item cherry-pick / revert
\item incoming / outgoing の差分表示
\item コミットの非同期実行（大きなリポジトリで待たされない）
\item 外部で git 操作したときのバッファ自動更新
\end{itemize}

とりあえず、事故防止に効くものだけでも入れておく価値がある。

\begin{verbatim}
(leaf vc
  :straight nil
  :custom
  (;; 公開済みの履歴を書き換えようとしたら止める（force push 事故の防止）
   (vc-allow-rewriting-published-history . nil)
   ;; コミットを非同期にする
   (vc-async-checkin                     . t))
  :config
  (vc-auto-revert-mode 1))
\end{verbatim}

「じゃあ Magit を消せるか」というと、そこは急がないほうがいい。
私は \textbf{まず VC 側を有効にして、1〜2か月ふつうに使ってみてから決める} つもりだ。
道具を捨てる判断は、実際に使ってみた実感でしか下せない。
\subsubsection{ターミナルの Emacs でもポップアップが出る}
\label{sec:org420e835}

これは地味だが大きい。

31 では、ターミナル（TTY）上の Emacs でも「子フレーム」が使えるようになった。
これまで GUI 版でしか出せなかった補完のポップアップ（ \texttt{corfu} など）が、
\texttt{emacs -nw} でも動く可能性がある。

一方で、同じ流れで \textbf{ターミナルのマウス操作モードが標準で有効になる} 変更も入った。
これは iTerm2 や Ghostty で「ドラッグして選択してコピー」ができなくなる、
という体感の変化を生む。

ターミナルで Emacs を使う人は、方針を決めておいたほうがいい。

\begin{verbatim}
;; 端末側のコピー&ペーストを優先したい場合
(unless (display-graphic-p) (xterm-mouse-mode -1))
\end{verbatim}
\subsubsection{macOS 向けの新機能がふたつ}
\label{sec:orgfb5cf3f}

私は Mac で Emacs を使っているので、これは嬉しかった。

\begin{itemize}
\item \texttt{system-taskbar-mode} — Dock アイコンにバッジや進捗バーを出せる
\item \texttt{system-sleep} — 長時間処理の最中にスリープするのを防げる
\end{itemize}

たとえば「Emacs 本体を自分でビルドしている最中に Mac が寝てしまう」という
地味な困りごとが、これで解決する。

\begin{verbatim}
(when (and (eq system-type 'darwin) (fboundp 'system-taskbar-mode))
  (system-taskbar-mode 1))
\end{verbatim}

さらに \texttt{native-comp-async-on-battery-power} という設定が増えた。
Emacs は裏でコードを機械語にコンパイルして高速化する仕組み（native-comp）を持っているが、
これがノートパソコンのバッテリーをけっこう食う。
バッテリー駆動中はコンパイルを止める、という指定ができるようになった。

\begin{verbatim}
(setopt native-comp-async-on-battery-power nil)
\end{verbatim}
\subsubsection{コードの折りたたみが実用レベルになった}
\label{sec:org52a6e6c}

Emacs には昔から \texttt{hideshow} という「関数を折りたたむ」機能があるのだが、
正直あまり使い勝手が良くなく、多くの人はサードパーティ製で代替していた。

31 でこれが一気に強化された。
折りたたみの循環（親→入れ子→全展開）、余白への目印表示、
隠れている行数の表示など、必要なものが一通り揃った。

\begin{verbatim}
(leaf hideshow
  :straight nil
  :hook ((prog-mode-hook . hs-minor-mode))
  :custom
  ((hs-show-indicators      . t)     ; 折りたたみ位置に目印を出す
   (hs-display-lines-hidden . t))    ; 何行隠れているか表示する
  :bind ((:hs-minor-mode-map
          ("<backtab>" . hs-cycle))))
\end{verbatim}
\subsubsection{移行するときに気をつけること}
\label{sec:orgd536905}

新しいバージョンに上げるとき、いちばん怖いのは「気づかないうちに壊れている」ことだ。
31 の NEWS には「互換性のない変更」という節があり、
そこから自分の設定に影響しそうなものを拾っておいた。

\begin{center}
\begin{tabular}{ll}
変更点 & どう困るか\\
\hline
\texttt{if-let} / \texttt{when-let} が非推奨に & 末尾に \texttt{*} が付いた形（=if-let*=）に書き換えが必要\\
ts-mode のインデント設定の変数名が変わった & 独自に設定していると効かなくなる\\
Pcase の入れ子バッククォートが使えない & \texttt{pcase} を凝った使い方をしていると壊れる\\
文字列の書き換え制限が厳しくなった & リテラル文字列を破壊的に変更するコードがエラーに\\
Org 9.8 が同梱される & 自分で Org のバージョンを固定していると二重管理になる\\
\texttt{site-start.el} の読み込み順が変わった & Homebrew などが置いたファイルの挙動が変わりうる\\
\end{tabular}
\end{center}

これらは、いきなり本番の設定に適用してハマるのではなく、
\textbf{ブランチを切って、ひとつずつ試す} のが確実だ。

私の場合はこういう手順で進めている。

\begin{enumerate}
\item \texttt{git switch -c feat/emacs31} でブランチを切る
\item 「自作コードを消す」系（tree-sitter、空白削除、タイマー）を先に適用する
\item 消した関数がどこかから呼ばれていないか grep で確認する
\item リスクの低い小さな設定をまとめて適用する
\item 大きめの新機能は \textbf{1項目ずつ} 入れて、そのつど起動時間とメモリを測る
\item 実測してから、不要になったパッケージを消す判断をする
\end{enumerate}

特に 5 が大事だと思っている。
「新機能を全部入れたら遅くなった」となったとき、
まとめて適用していると、どれが原因かわからなくなる。
\subsubsection{結局、何が得られるのか}
\label{sec:org8e319ae}

数字で言えば、こうなる。

\begin{center}
\begin{tabular}{lll}
項目 & 現状 & 移行後\\
\hline
tree-sitter 設定 & 約155行 & 約55行\\
自作タイマー & 手書き & 設定項目1つ\\
自作デバウンス & 3か所 & ライブラリ呼び出し\\
削除できるパッケージ & — & 最大5個\\
\end{tabular}
\end{center}

ただ、正直なところ \textbf{行数が減ること自体はどうでもいい} 。

本当に意味があるのは、
「自分が保守しなければならないコード」が
「Emacs 本体が動作を保証してくれるコード」に置き換わったことだ。

自作コードは、Emacs がバージョンアップするたびに壊れる可能性がある。
本体の機能は、そう簡単には壊れない（壊れるときは NEWS に書いてある）。

設定を育てるというのは、コードを足していくことだと思われがちだが、
実際には \textbf{「本体が追いついたら、自分のコードを引っ込める」} という
引き算の作業も同じくらい重要なのだと、今回あらためて感じた。
\subsubsection{おまけ：自分で確かめる方法}

半分は職業病みたいなものかもしれない。「動いていると言われているもの」

\subsubsection{そもそも gnumach って何なのか}
\label{sec:orgf7f1fe3}

\href{https://github.com/flavioc/gnumach}{GNU Mach} は、GNU Hurd の土台になっている
マイクロカーネルだ。ルーツを辿ると Carnegie Mellon 大学の Mach 3.0 に
行き着く、由緒正しい(?)1980年代の設計。「マイクロカーネル」という
言葉の教科書的な説明——「カーネルはメカニズムだけ提供し、ポリシーは
ユーザ空間に追い出す」——を、これほど愚直に実装しているコードベースも
珍しいんじゃないかと思う。

ディレクトリ構成を見るだけでも性格がわかる。

\begin{center}
\begin{tabular}{lll}
ディレクトリ & 中身 & 規模\\
\hline
\texttt{kern/} & スケジューラ・タスク/スレッド管理 & 約31,500行\\
\texttt{ipc/} & Mach IPC(ポート・メッセージング) & 約16,600行\\
\texttt{vm/} & 仮想メモリ管理 & 約21,200行\\
\texttt{device/} & デバイス抽象層 & 約9,700行\\
\texttt{linux/} & Linuxから移植したドライバ群 & 約345,500行\\
\end{tabular}
\end{center}

見ての通り \texttt{linux/} が圧倒的に大きいんだけど、これは中身がMachというより
「LinuxのドライバをMachの作法でラップしたもの」がほとんどだからだ。
IDE/SCSI/AHCIのディスクドライバやネットワークカードのドライバを、いちいち
Machのために書き直すのは非現実的なので、既存資産を持ってきている。この
あたりの「潔さ」は好きだ。

肝心の「マイクロカーネルらしさ」が詰まっているのは \texttt{kern/} ・ \texttt{ipc/} ・ \texttt{vm/}
の3つで、合計しても7万行に満たない程度。今回はほぼこの3つだけを読んだ。
\subsubsection{一番おもしろかった:ポートは「番号」でしかない、という設計}
\label{sec:org1e78284}

Mach IPCの根幹は「すべてはポートへのメッセージ送信である」という一文に
尽きる。ファイルもプロセスもメモリオブジェクトも、カーネルの目からは
「ポート」という統一的な窓口を通してやり取りされる。

で、実際にコードを読んでいちばん「なるほど」と思ったのが、ユーザ空間から
見えている「ポート」の正体だ。 \texttt{ipc/ipc\_kmsg.c} の \texttt{ipc\_kmsg\_copyin\_header}
という関数(送信メッセージのヘッダを処理する箇所)を読むと、こう書いて
ある。

\begin{verbatim}
is_read_lock(space);
entry = ipc_entry_lookup(space, dest_name);      // 名前→エントリ
...
dest_port = (ipc_port_t) entry->ie_object;
ip_lock(dest_port);
is_read_unlock(space);
...
dest_port->ip_srights++;                          // 参照カウント増加
\end{verbatim}

つまりユーザ空間が持っている「ポート」というのは、実体としてはただの
整数(\texttt{mach\_port\_name\_t})だ。カーネルオブジェクトへのポインタなんて
どこにも渡っていない。その整数を、必ず「呼び出したタスク自身のIPC
空間」というテーブルに引かせて、初めて実オブジェクトのポインタが手に
入る。

これがどういう意味を持つかというと、*他人のポート番号を知っていても、
それだけでは何もできない* ということだ。番号が指すテーブルは常に
「自分の空間」なので、他タスクの空間を覗く経路がAPIレベルで存在しない。
UNIXのファイルディスクリプタと似ているようで、「送信権」「受信権」を
はっきり区別した、もう一段厳格なケーパビリティモデルになっている。

しかも権利を人に渡すときのコストが、渡し方によってきっちり作り分けられて
いるのも面白いところだ。 \texttt{ipc/ipc\_right.c} の \texttt{ipc\_right\_copyin} を見ると:

\begin{itemize}
\item \texttt{MAKE\_SEND} (受信権から新しい送信権を複製する)は、単に参照カウントを
増やすだけ
\item \texttt{MOVE\_SEND} (自分の送信権を他人に渡して、自分は手放す)は、内部の
「ユーザ参照カウント(urefs)」をちゃんとデクリメントし、0になったら
エントリごと消す
\end{itemize}

「コピーする」と「明け渡す」で明確にコード上の扱いが違う、というのは、
1980年代の設計とは思えないほど几帳面だなと感心した。
\subsubsection{ページフォールトの中身は、ほぼ「シャドウチェーンを遡る」だけ}
\label{sec:org3fec270}

もう一つ面白かったのが仮想メモリ側、 \texttt{vm/vm\_fault.c} のページフォールト
処理だ。

Machのメモリオブジェクトは「シャドウチェーン」という親子関係を持って
いて、あるページが自分のオブジェクトに無ければ親を見に行く、という
仕組みになっている。コードで言うとこの部分だ。

\begin{verbatim}
if (m->absent) {
    offset += object->shadow_offset;
    next_object = object->shadow;
    if (next_object == VM_OBJECT_NULL) {
        /* シャドウチェーンの末端 = ゼロフィルページを生成 */
        real_m = vm_page_grab(VM_PAGE_HIGHMEM);
        ...
        vm_page_zero_fill(m);
    }
    /* else: 親オブジェクトを見に行く */
}
\end{verbatim}

これ、要するに \texttt{fork()} したあとの匿名メモリ(ヒープやBSS)がどう実現
されているか、そのものだ。「無ければ親を見る、それでも無ければゼロで
埋める」——たったこれだけのルールの積み重ねで、プロセスのメモリ空間が
成立している。

Copy-on-Writeの実装も同じ発想の延長で、書き込みが起きた瞬間に「元の
ページの中身を、コピー先のオブジェクトに逃がしてから」元を書き換え
可能にする、という順序を守っているだけだ。派手な仕掛けは何もなくて、
地味なルールの積み重ねだけでOSの根幹機能が成立しているのを見ると、
なんというか、静かに感動する。
\subsubsection{カーネルがポリシーを持たない、を本当に徹底している話}
\label{sec:org06dd3ef}

個人的に一番「これは筋がいい設計だ」と思ったのが、VMのコピー戦略の
決め方だ。

\texttt{vm/vm\_object.c} の \texttt{vm\_object\_copy\_strategically} という関数は、メモリを
コピーするときに「即座に全部コピーする」「遅延COWにする」「ページャに
丸投げする」の3通りをswitchで切り替えているんだけど、この戦略を
\textbf{カーネル自身は決めていない} んだよね。

\begin{verbatim}
while (!src_object->pager_ready) {
    vm_object_wait(src_object, VM_OBJECT_EVENT_PAGER_READY, interruptible);
    ...
}
\end{verbatim}

外部のページャ(ユーザ空間で動くサーバプロセス)が「私が管理するこの
メモリはこの戦略でコピーしてください」と申告してくるのを、カーネルは
律儀に待つだけなのだ。申告が届くまではコピー処理そのものをブロック
する。

Hurd側の対応も追ってみたら、ファイルシステム翻訳者(ext2fsなど)が
使う \texttt{libpager} というライブラリの \texttt{pager\_create()} 関数が、まさに
この \texttt{copy\_strategy} を引数として受け取っていた。実行ファイルや
共有ライブラリのマップに使われる「遅延COW」は、カーネルが勝手に判断
しているのではなく、ファイルシステム側のサーバが「これは遅延COWで
いいですよ」と明示的に宣言しているから成立している、ということだ。

「メカニズムはカーネル、ポリシーはユーザ空間」という設計哲学、教科書
では何度も見た文言だけど、実際にコードでここまで愚直に貫かれていると、
ちょっと感動してしまう。
\subsubsection{余談:25年前に読んでいたのはHurd側だった}
\label{sec:orgcb69d0a}

ここで少し個人的な話をしたい。今回gnumach(カーネル側)を読んで
いて気づいたんだけど、実は25年ぐらい前、一度Hurd/gnumachのソースを
読もうとしたことがある。当時惹かれていたのは
カーネル側ではなく、Hurd側の \textbf{translator} という仕組みだった。

translatorというのは平たく言うと「ファイルシステムのノード1つ1つに、
好きなユーザ空間サーバを貼り付けられる」機構だ。`settrans`コマンド
一発で、あるディレクトリの正体を任意のプログラムにすり替えられる。
2005年前後にFUSEが登場したときに「これは便利だ」と持て囃されたけど、
Hurdはその発想をずっと早く、しかもマウントポイント単位の局所的な話
ではなく、ファイルシステム階層そのものの設計原理としてやっていた。

当時特に読んでいたのは \texttt{pfinet} だ。ネットワークをファイルシステムの
translatorとして実装するという、今思えばかなり大胆な発想だった。今回
gnumachを読み返したついでに、記憶を頼りに \texttt{pfinet} のソースも覗いて
みたところ、READMEにこう書いてあった。

\begin{quote}
"The Hurd's pfinet server is based on networking code taken from the
Linux kernel sources, initially version 2.2.12 of Linux."
\end{quote}

つまり中身は文字通り、 \textbf{Linux 2.2.12のTCP/IPスタックをほぼそのまま移植したもの} だ。
\texttt{pfinet/linux-src/net/\{core,ipv4,ethernet\}} という
ディレクトリがまるごと存在していて、外側の \texttt{socket-ops.c} ・ \texttt{io-ops.c}
がHurdのRPC作法(`io\_read`/`io\_write`、`socket\_create`など)を実装し、
内側でそのままLinuxのソケットコードを叩く、という二層構造。前段で
書いた「translatorは`memory\_object`の発想の応用である」という話で
言うと、pfinetは「ネットワークスタックという巨大な機能ブロックを丸ごと
ユーザ空間サーバに閉じ込めた」かなり極端な例だったんだと思う。
カーネルはネットワークのことを一切知らない。

当時は結局、自分でtranslatorを書くところまでは至らず、読むだけで
終わった。`trivfs`まわりの作法(`trivfs\_S\_dir\_lookup`のあたり)を
理解しようとしたところで力尽きた記憶がある。それでも、25年経って
また同じコードの子孫を読み返すことになるとは思っていなかったので、
不思議な巡り合わせだった。

ちなみに、25年前の設計が令和のいまも現役だという証拠に、2026年Q2の
Hurd開発ニュースにもちょうどpfinetの話が出ていた。 \texttt{mmap} の戻り値
をチェックせずに使っていた古いバグが2つ見つかり、メモリが逼迫すると
pfinetがクラッシュしうる、という修正が最近入ったばかりだったそうだ。
1999年頃のコードが、2026年になっても現役でバグ報告と修正を受けている
というのは、なかなか感慨深いものがある。
\subsubsection{aarch64移植、見た目と実態のギャップが面白かった}
\label{sec:orgaa5cda7}

ここからは余談。gnumachには \texttt{aarch64/} というディレクトリがあって、
「お、ARM移植も進んでるのか」と覗いてみたら、中身は型定義とABIの
ヘッダファイルだけで、 \texttt{.c} ファイルが1つも無い。ブートコードも例外処理
コードも見当たらない。

「あれ、これって看板倒れなのでは……」と思ってコミットログを辿ったら、
直近のコミットメッセージにこんな一文があった。

\begin{quote}
"Bugaev's wip-aarch64 worked around this by editing kern/lock.h itself\ldots{}"
\end{quote}

つまり、実際に動くARM移植は別ブランチ(\texttt{github.com/bugaevc/gnumach} の
\texttt{wip-aarch64})に存在していて、mainリポジトリには型定義だけが先行して
着地している状態だった。少し検索してみたところ、開発者本人が

\begin{quote}
"my branch of gnumach compiles, boots in QEMU, and passes the testsuite!"
\end{quote}

と、2024年の時点でQEMU上でブートしてテストスイートまで通していると
報告していて、fork()やシグナル配送(intr RPC → シグナルトランポリン →
sigreturn)まで一通り動く状態になっているとのこと。2026年に入ってからは、
別の開発者がこの動くブランチを「共有ファイルを一切壊さずにmainへ
段階的に取り込む」という、地味だけど誠実な作業を進めているようだ。

コミットログという「表の記録」だけを見ていると進捗を過小評価してしまう
典型例だったな、と反省した。オープンソースのアーキ移植って、動く
実装があってもupstream化には別の労力がかかるんだな、というのを実感
した瞬間だった。
\subsubsection{直近のバグ修正から見える、地味だけど大事な話}
\label{sec:orgd9db471}

最後にもう一つ、コミット履歴を追っていて印象に残ったバグ修正を紹介
する。

ひとつは、SMP環境でスケジューラがNULLポインタを踏んでカーネルパニック
していたバグ。コミットメッセージには「Hurdを自己ホストビルドしている
最中にSMP環境でクラッシュする」とあって、地味に実害の大きいバグだった
んだろうなと想像がつく。

もうひとつは、もう少し本質的な話。 \texttt{task\_priority()} という
RPC——タスク自身が自分の優先度を変更するための呼び出しなんだけど、特権
ポートを一切要求しない、つまり \textbf{どのプロセスでも呼べる} ものだ。
これに、修正前は上限チェックが一切なかった。

\begin{verbatim}
task_lock(task);
if (task->max_priority > priority) {      // ← 追加されたチェック
    task_unlock(task);
    return KERN_NO_ACCESS;
}
task->priority = priority;
\end{verbatim}

Machの優先度は数値が小さいほど「偉い」扱いなので、これはつまり「誰でも
自分を最優先に格上げできてしまい、他のタスクを飢餓状態に追い込める」
状態だったということだ。修正では \texttt{max\_priority} という天井を導入し、
それを超える要求は拒否するようにしていた。

CVE番号が付くような華々しい脆弱性ではなく、開発者自身が地道なコード
レビューで見つけて塞いだ類の話だと思うけど、「マイクロカーネルに
おいて、タスクポートは無制限の自己管理権限ではない」という信頼境界を
守る、というのはまさにこのOSの根幹に関わる話だよなと感じた。
\subsubsection{まとめ}
\label{sec:org001eee0}

読んでみて改めて思ったのは、gnumachというコードベースは全体としては
「枯れた設計」なんだけど、枯れているからこそ設計思想がむき出しで見える、
という面白さがあるということだった。ポートは番号でしかない、コピー
戦略はユーザ空間が決める、カーネルは律儀に待つ——1980年代に確立された
アイデアが、令和のいま2026年のコミットログの中でも変わらず一貫して
守られているのを見るのは、なかなか得難い体験だった。

気が向いたら、スケジューラ(\texttt{sched\_prim.c})のロードバランシング周りも
続けて読んでみようと思う。
\subsection{{\bfseries\sffamily DONE} evalの中身を覗いてみた ─ Emacsが40年抱えてきた矛盾の話}
\label{sec:org85d579b}
普段は \texttt{README.org} をいじって設定を壊しては直す、という生活をしているが、たまには自分が毎日呼び出している \texttt{eval} が実際どう動いているのか見てみたくなった。というわけでGNU Emacs本体のCソース、 \texttt{src/eval.c} (4,700行弱)を読んでみた記録。読み終えて分かったのは、この評価器が「言語処理系としての正しさ」より「1985年から動いているコードを1行も壊さないこと」を一貫して優先し続けてきた、継ぎ足しの塊だということだった。
\subsubsection{eval\_subという名の交通整理係}
\label{sec:orgfb634b2}

Emacs Lispで何かを評価するとき、内部では \texttt{eval\_sub} という関数がすべてのS式を捌いている。中身は驚くほど単純な分岐だ。

\begin{itemize}
\item コンスセルでなければ、そのまま返す(数値や文字列の「自己評価」)
\item シンボルなら、変数として値を引く
\item コンスセルなら、関数呼び出しか特殊形式かをさらに判定する
\end{itemize}

コンスセルの場合の分岐がこの関数の本体で、先頭要素(関数名にあたる部分)の型によって以下のように処理が分かれる。

\begin{itemize}
\item Cで書かれたプリミティブ(SUBR)ならC関数を直接呼ぶ
\item レキシカルクロージャやネイティブコンパイル関数なら \texttt{apply\_lambda} に委譲
\item \texttt{(macro . 関数)} という形のコンスセルならマクロとして展開してから再評価
\item \texttt{(lambda ...)} という生のコンスセルなら、これも \texttt{apply\_lambda} に委譲
\end{itemize}

面白いのは、Emacs Lispの「関数」が実際には少なくとも4通りの異なる内部表現(Cのポインタ、コンパイル済みクロージャ、生のconsラムダ、ネイティブコード)を持っているのに、呼び出し側からはその違いが完全に隠蔽されている点だ。標準関数を後からユーザーが純Lispで再定義しても、呼び出し規約はまったく同じまま動く。
\subsubsection{特殊形式は「引数を評価しないC関数」でしかない}
\label{sec:org0601ad0}

\texttt{if} や \texttt{let} や \texttt{while} といった特殊形式は、 \texttt{UNEVALLED} という印がついたSUBRとして定義されている。

\begin{verbatim}
DEFUN ("if", Fif, Sif, 2, UNEVALLED, 0, ...)
  (Lisp_Object args)
{
  Lisp_Object cond = eval_sub (XCAR (args));
  if (!NILP (cond))
    return eval_sub (Fcar (XCDR (args)));
  return Fprogn (Fcdr (XCDR (args)));
}
\end{verbatim}

つまり \texttt{(if cond then else)} と書いたとき、Emacsは \texttt{cond} の部分だけを評価してから、Cのif文で \texttt{then} か \texttt{else} のどちらを評価するかを自分で決めている。マクロ展開という別フェーズがあるわけではなく、評価器がその場その場で「これは何を評価すべきか」を判断しているだけ、というのが素朴で好きなところだ。ちなみに \texttt{if} の内部で \texttt{else} 節の評価を丸ごと \texttt{Fprogn} に投げているのを見ると、「 \texttt{if} は \texttt{progn} に依存して実装されている」という実装同士の依存関係も透けて見える。
\subsubsection{nilが自分自身を返す理由}
\label{sec:org917ba67}

\texttt{nil} を評価すると \texttt{nil} が返るのは当たり前に思えるが、実はシンボルなので本来は「変数として値を引く」経路を通るはずだ。種を明かすと、 \texttt{nil} ・ \texttt{t} ・キーワードシンボルは初期化時に「自分自身を値として持つ」よう仕込まれた上で、書き換え禁止フラグ(\texttt{SYMBOL\_NOWRITE})が立てられている。 \texttt{data.c} の \texttt{set\_internal} を見ると、このフラグが立ったシンボルへの再代入は問答無用でエラーになる(キーワードが自分自身に再設定される場合だけ例外)。

見た目の「自己評価」と、C言語レベルでの実装はまったく別物というのが地味に面白かった。アトムの自己評価は「コンスでなければスルーする」だけの話で、 \texttt{nil} / \texttt{t} /キーワードの自己評価は「シンボルの値セルが定数として固定されている」という、まったく別の仕組みで実現されている。
\subsubsection{レキシカルスコープを動的束縛の上に建て増しした話}
\label{sec:orgf9cbb96}

一番驚いたのはここだ。Emacs Lispは今でこそレキシカルスコープ(クロージャがちゃんと変数を閉じ込める方式)を使えるが、これは後付けの機能で、しかも \textbf{内部実装はダイナミックスコープの仕組みをそのまま流用} している。

具体的には、レキシカル環境そのものが \texttt{Vinternal\_interpreter\_environment} という、特殊変数(つまりダイナミックに束縛される変数)の中にalistとして格納されている。 \texttt{let} でレキシカル変数を作るというのは、実は「環境alistというダイナミック変数に新しいコンスセルをconsして、それをまたダイナミックに束縛し直す」という操作に過ぎない。土台はダイナミックスコープのまま、その上にレキシカルスコープごっこを乗せているような設計だ。

そして、シンボルごとに「動的」か「レキシカル」かを切り替えるのが \texttt{declared\_special} フラグだ。これは \texttt{(defvar sym val)} のように初期値つきで宣言すると立つ、シンボルに一生ついて回るグローバルな印になる。

さらに面白いのが \texttt{(defvar foo)} (初期値なし)の挙動だ。これは、そのシンボルを「このスコープでは動的扱いにする」という \textbf{一時的な} 目印として、環境alistに \textbf{コンスセルではなく裸のシンボル} を突っ込む。

\begin{verbatim}
Vinternal_interpreter_environment
  = Fcons (sym, Vinternal_interpreter_environment);
\end{verbatim}

変数参照コードは \texttt{Fassq} (コンスセルのcarを探す関数)を使うので、裸のシンボルには絶対にヒットしない。一方 \texttt{let} 側は \texttt{Fmemq} (リストの要素そのものが \texttt{eq} で一致するか探す関数)でこの裸シンボルを検出し、レキシカル束縛をやめて動的束縛に切り替える。

\begin{itemize}
\item 実際の束縛エントリ \texttt{(var . val)} はコンスセルなので、 \texttt{var} そのものとは \texttt{eq} にならない → \texttt{Fmemq} には引っかからない
\item 裸のシンボル \texttt{var} は \texttt{var} そのものなので → \texttt{Fmemq} に引っかかる
\end{itemize}

\textbf{同じ1本のリストの中に、意味の違う2種類のエントリを型の違いだけで共存させている} わけで、なるほどLispらしいと唸った。 \texttt{README.org} の中で \texttt{(defvar my-var)} とだけ書いて後から \texttt{setq} する、というのをよく見かけるが、あれはまさにこの仕組みで「レキシカルスコープのファイル内でも、このシンボルだけは意図的に動的変数として扱わせる」というテクニックだったことになる。
\subsubsection{関数呼び出しの中身: apply\_lambdaとfuncall\_lambda}
\label{sec:org327203e}

関数呼び出し(SUBRでもマクロでもない、通常のクロージャやラムダ呼び出し)は \texttt{apply\_lambda} → \texttt{funcall\_lambda} という2段構えになっている。

\texttt{apply\_lambda} は未評価の引数リストを評価してCの配列に詰めるだけの前処理で、本体は \texttt{funcall\_lambda} にある。ここでは関数の型によって処理が4通りに分かれる。

\begin{itemize}
\item 生の \texttt{(lambda (args) body)} 形式のコンスセル → 動的束縛前提
\item バイトコンパイル済みのレキシカルクロージャ → 引数束縛すら経ずに \texttt{exec\_byte\_code} へ直行
\item インタプリタ実行のクロージャ → コンスタントスロットからレキシカル環境を取得
\item ネイティブコンパイル関数 → \texttt{lambda\_list} から引数名を取得
\end{itemize}

ここでも「レキシカルバイトコードだけは引数束縛ループを一切通らずバイトコードエンジンに丸投げする」という最適化があって、バイトコード自身がスタックから引数を取る命令を持っているから、C側での束縛処理がそもそも不要という理屈だ。

そのあとの \texttt{\&optional} / \texttt{\&rest} を処理する引数束縛ループも中身は素朴で、仮引数リストを1つずつ辿りながら \texttt{\&rest} なら残り全部をリスト化、 \texttt{\&optional} 中で引数が足りなければ \texttt{nil} を補う、という具合。そして最後に束縛するとき、 \texttt{let} のときとまったく同じロジック(\texttt{lexenv} が非nilならconsしてレキシカル、そうでなければ \texttt{specbind} で動的)が繰り返される。つまり「引数の束縛」と「 \texttt{let} の束縛」は、Emacsの内部では同じ1つの判断ロジックのコピーなのだ。
\subsubsection{specpdlという名の何でも屋スタック}
\label{sec:orgb13633f}

動的束縛(\texttt{specbind})がどう元に戻るのかを追うと、 \texttt{specpdl} という単一のスタックに行き着く。 \texttt{lisp.h} の \texttt{specbind\_tag} 列挙型を見ると、このスタックが担っているのは変数の巻き戻しだけではないことが分かる。

\begin{itemize}
\item 動的束縛(通常のletバインディングと、バッファローカル変数用のバリエーション)
\item \texttt{unwind-protect} のクリーンアップ関数
\item バックトレース情報
\item モジュール(動的ロード拡張)のランタイムや環境
\end{itemize}

性質の異なるものを1本のスタックに統一し、 \texttt{unbind\_to} を1回呼ぶだけで「変数を元に戻す」「クリーンアップ関数を呼ぶ」「バックトレースを巻き戻す」が同時に処理される。C言語には例外機構がないので、 \texttt{condition-case} や \texttt{unwind-protect} の巻き戻しは \texttt{setjmp} / \texttt{longjmp} とこの単一スタックの組み合わせだけで実現されている。
\subsubsection{autoloadは「関数の中身」に仕込まれた偽物}
\label{sec:orgc556929}

意外だったのが \texttt{autoload} の実装だ。シンボルの関数セルに \texttt{(autoload FILE ...)} というプレースホルダーが入っていると、 \texttt{eval\_sub} はファイルをロードしてから同じ評価を \texttt{goto retry} でやり直す。

関数を呼ぶたびに「これは本物の関数か、それとも遅延ロードの目印か」を毎回チェックする設計は、標準ライブラリを起動時に全部ロードしないための仕組みで、Emacsの起動速度を支える地味な根幹になっている。 \texttt{straight.el} 経由で入れているパッケージの大半は、初回呼び出しまでこの \texttt{autoload} プレースホルダーのまま待機している。
\subsubsection{40年分の後方互換性という重み}
\label{sec:org1da72fd}

こうして読んでいくと、Emacsが「正しい言語設計」より「既存コードを壊さないこと」を一貫して優先してきたのがよく分かる。1985年当時のダイナミックスコープ前提のコードを今も動かしながら、レキシカルスコープもネイティブコンパイルもバイトコードエンジンも生やしていく。1つの変数が「シンボル単位で動的かレキシカルかを選べる」というのも、1つのalistが「型によって2つの意味を持つ」というのも、本来なら言語設計としては褒められたものではないかもしれない。しかし、後方互換性という制約の中でここまで機能を積み増してきた継ぎ足しの跡が、そのまま設計として残っているのを見るのは素直に楽しい。

次はバイトコードエンジン(\texttt{bytecode.c})か、 \texttt{condition-case} / \texttt{catch}-\texttt{throw} の非局所脱出まわりを読んでみようと思っている。

\label{sec:org5afcb48}

きっかけは単純だった。Emacsでいつも通り \texttt{\textasciitilde{}/.authinfo.gpg} を開こうとしたら、こんなエラーが出た。

"I/O error during SQL operation" ってなんだ。GPGでSQLのエラーが出るのを初めて見た。
\subsubsection{keyboxdとSQLite、そしてGnuPG 2.5系という沼}
\label{sec:org2ee394e}

調べていくと、GnuPGは2.4系くらいから公開鍵の管理を \texttt{keyboxd} というデーモン経由でSQLiteバックエンド(\texttt{pubring.db})に持たせる方式に移行しつつある。自分の環境は \texttt{brew list -{}-{}versions gnupg} で確認したところ \texttt{2.5.21} 。これはdevel版ではなく、Homebrew-coreが配布している現行の安定版らしい（GnuPGは2025年にバージョニング体系を変えていて、2.5.x系列がメインラインになっている）。

一つずつ潰していった。

\begin{itemize}
\item ロックを握っているプロセスがいないか（ \texttt{lsof} → 何も出ない）
\item \texttt{pubring.db} のパーミッションは \texttt{600} で問題なし
\item \texttt{xattr -l} で見ると \texttt{com.apple.provenance} だけ。怪しいquarantine属性ではない
\item \texttt{sqlite3 pubring.db "PRAGMA integrity\_check;"} → \texttt{ok}
\item ボリュームはローカルAPFS。ネットワークドライブでも同期ストレージでもない
\end{itemize}

ファイルは壊れていない。ロックもない。パーミッションも正常。それでも "I/O error during SQL operation" が出続ける。

こういうとき一番早いのは、原因を完全に特定することより「迂回する」ことだったりする。
\subsubsection{pubring.kbxへの切り戻しで即解決}
\label{sec:orga03ff06}

keyboxdのSQLiteパスをそもそも通らないようにする。レガシー形式の \texttt{pubring.kbx} に戻すだけだ。

\begin{verbatim}
gpgconf --kill all
sed -i '' '/^use-keyboxd$/d' ~/.gnupg/common.conf
mv ~/.gnupg/public-keys.d ~/.gnupg/public-keys.d.broken.$(date +%Y%m%d)
gpgconf --kill all
gpg --list-keys
\end{verbatim}

\begin{verbatim}
gpg: keybox '/Users/ac1965/.gnupg/pubring.kbx' が作成されました
\end{verbatim}

これで "I/O error during SQL operation" は綺麗さっぱり消えた。もちろん公開鍵は空っぽになるので、その後は秘密鍵（ \texttt{private-keys-v1.d} は無傷で残っている）に対応する公開鍵を再インポートする作業が必要になる。

まだ枯れきっていないバックエンドを無理に使い続けるより、確実に動く方に倒す。今回はそれが正解だった。
\subsubsection{ついでにTouch ID化した}
\label{sec:org167c128}

.authinfo.gpg を開くたびにパスフレーズを打つのも面倒だったので、この機会に \texttt{pinentry-touchid} を導入してTouch ID認証に置き換えた。 \texttt{gpg-agent.conf} はこうなっている。

\begin{verbatim}
allow-loopback-pinentry
default-cache-ttl 1800
# allow-emacs-pinentry
pinentry-program /opt/homebrew/bin/pinentry-touchid
\end{verbatim}

\texttt{allow-emacs-pinentry} はあえてコメントアウトしてある。有効にするとEmacsのミニバッファ入力が優先されるケースがあり、Touch ID方式と競合するからだ。
\begin{enumerate}
\item 共通鍵暗号のファイルをTouch IDで復号するときの注意
\label{sec:org3da6a7f}

ここでちょっと引っかかった。 \texttt{pinentry-touchid} は「公開鍵の秘密鍵」と「共通鍵（パスフレーズだけの \texttt{gpg -c}  ）暗号化ファイル」を区別しない。仕組みを見ると、gpg-agentが渡してくる cache-id をキーにmacOSのKeychain（サービス名 \texttt{GnuPG} ）を検索しているだけで、キー種別には興味がない。

つまり共通鍵暗号のファイルにTouch IDを使うと、 \textbf{そのファイルを復号するためのパスフレーズそのものがKeychainに保存される} ことになる。Touch IDは「読み出しのゲート」であって、パスフレーズがSecure Enclaveに守られるわけではない。公式READMEにもそう明記されていた。

はじめは「Touch ID＝安全」と直感的に思ってしまいそうになるが、それは半分正しくて半分違う。以下、実際に運用する上で気をつけていること。

\begin{itemize}
\item \texttt{default-cache-ttl} はgpg-agent自身のメモリキャッシュにしか効かない。Keychainのエントリは手動削除しない限り無期限に残る
\item \texttt{gpg -{}-{}symmetric} は暗号化のたびにS2K saltが変わるので、同じパスフレーズでもファイルが変わるとcache-idも変わり、Keychain未登録扱いになって再度手動入力が必要になることがある。だから毎回中身が変わるファイルより、頻繁に開く1つのファイル（ \texttt{.authinfo.gpg} みたいな）に使うのが現実的
\item どうしても気になる場合は、共通鍵暗号ではなく公開鍵暗号に切り替えるのが筋がいい。その場合Touch IDがガードするのは「秘密鍵へのアクセス」であって、秘密鍵自体は \texttt{\textasciitilde{}/.gnupg/private-keys-v1.d} にファイルとして存在する。パスフレーズをKeychainに丸ごと預けるのとは性質が違う
\end{itemize}

結論として、今回は復号頻度の高い \texttt{.authinfo.gpg} 用途だと割り切ってTouch ID化した。重要度の高いファイルは引き続き公開鍵方式のままにしてある。
\item Keychainへの登録、実は pinentry-mac の仕事
\label{sec:orgf593712}

ここでちょっと訂正しておきたいことがある。「Touch IDでパスフレーズをKeychainに保存する」と書いたが、正確には \texttt{pinentry-touchid} 自身はKeychainへの書き込みを一切やっていない。書き込み・登録の実体は \texttt{pinentry-mac} が持っていて、 \texttt{pinentry-touchid} はそこに登録済みのエントリをTouch ID認証つきで読みに行くだけ、という役割分担になっている（公式READMEに明記されている）。

なので実際にKeychainへ登録する一連の流れはこうなる。

\begin{verbatim}
# 事前に、pinentry-macにKeychain保存を許可しておく
defaults write org.gpgtools.common UseKeychain -bool yes
\end{verbatim}

その状態でパスフレーズ入力が必要な操作（ \texttt{gpg -as -} でも実際の復号でもいい）を行うと、 \texttt{pinentry-mac} のダイアログに「Save in Keychain」のチェックボックスが出る。ここにチェックを入れると、続けてmacOSのログインパスワード入力を求められることがある。これは \texttt{pinentry-mac} や \texttt{pinentry-touchid} がこのエントリにアクセスする権限をOSから正式に認可してもらうためのもので、ここで \textbf{Always Allow} を選んでおく。

さらに \texttt{pinentry-touchid} 側でも初回のTouch ID認証時に、同じように「このエントリへのアクセスを許可するか」を聞かれることがある。README曰く：

\begin{quote}
If a password entry is found but is not "owned" by the pinentry-touchid program after the successful authentication with Touch ID, a normal password will be shown. [\ldots{}] In this dialog click Always allow after entering the password.
\end{quote}

ここでも Always Allow。二段階の認可を経て、ようやく完全にTouch IDだけで完結するようになる。

登録できたかどうかはCLIから確認できる。

\begin{verbatim}
security find-generic-password -s 'GnuPG'
\end{verbatim}

属性の一覧が返れば登録済み。何も見つからなければ次のようなエラーになる。

\begin{verbatim}
security: SecKeychainSearchCopyNext: The specified item could not be found in the keychain.
\end{verbatim}

パスフレーズの権限が完全に \texttt{pinentry-touchid} 側に移った後は、 \texttt{pinentry-mac} 側からの新規書き込みを止めておくとよい。README側も推奨している設定。

\begin{verbatim}
defaults write org.gpgtools.common DisableKeychain -bool yes
\end{verbatim}

エントリを消したいとき（パスフレーズをローテートした時など）は、これも \texttt{security} コマンド一発。

\begin{verbatim}
security delete-generic-password -s 'GnuPG' -a '<アカウント名>'
\end{verbatim}

\texttt{<アカウント名>} は \texttt{find-generic-password -s 'GnuPG'} で返ってくる属性一覧の中の \texttt{acct} の値。gpg-agentが渡すcache-idがベースになっているので、事前に確認してから使う。

「Touch IDが魔法のように守ってくれている」わけではなく、中身は地道な \texttt{pinentry-mac} ↔ Keychain ↔ \texttt{pinentry-touchid} の権限委譲の積み重ねだと分かると、何かあったときの切り分けもしやすくなる。



\begin{itemize}
\item \texttt{gpg-agent} まわりの "I/O error during SQL operation" は、keyboxd/SQLiteバックエンド固有の問題である可能性が高い。ロック・パーミッション・xattr・ファイルシステムをひと通り疑ってダメなら、素直に \texttt{pubring.kbx} に切り戻すのが早い
\item \texttt{pinentry-touchid} は便利だが、内部的には「Touch IDでKeychainのエントリを読み出しているだけ」という理解を持って使う。特に共通鍵暗号ファイルに使う場合は、パスフレーズ自体がKeychainに常駐する点を踏まえて、対象ファイルの重要度を見極める
\end{itemize}

トラブルシューティングは大体こういう順番で潰していくと迷わない。

\begin{enumerate}
\item ロック（他プロセスが握っていないか）
\item パーミッション・所有者
\item ファイル自体の整合性（今回なら \texttt{PRAGMA integrity\_check} ）
\item 環境要因（xattr、ファイルシステム、同期ストレージ）
\item それでもダメならバックエンド自体を疑う
\end{enumerate}

同じ沼にハマった人の参考になれば。
\end{enumerate}

date_line="$(grep -m1 -E '^(date|publishDate)[[:space:]]*[:=]' "${md_file}" 2>/dev/null || true)"
...
if [[ -z "${month:-}" ]]; then
    month="$(date +%m)"   # ← ここ
    warn "front matterにdateが見つからないため実行時月(${month})にフォールバック"

\subsubsection{穴その3: 自作プロパティ名は、ox-hugoにとってただの飾り}
\label{sec:org2ba4a47}

ここまでの調整で「custom画像をfront matterで明示指定する」仕組み自体は組み上がって
いたのだけど、いざ動かしてみると効かない。 \texttt{all-posts.org} 側には確かに指定を
書き込んだのに、書き出された \texttt{.md} のfront matterに一向にその項目が出てこない。

原因は間抜けなもので、 \texttt{:EXPORT\_HUGO\_COVER:} という \textbf{自分で思いついたプロパティ名} を
そのまま使っていたこと。ox-hugoは \texttt{EXPORT\_FILE\_NAME} や \texttt{EXPORT\_HUGO\_TAGS} のような、
あらかじめ決められた既知のプロパティしかfront matterに変換してくれない。任意の
キーを追加したいなら、 \texttt{EXPORT\_HUGO\_CUSTOM\_FRONT\_MATTER} というplist形式の受け皿を
使うのが正解で、思いつきで名前を作っても黙って無視されるだけだった。

\begin{verbatim}
;; NG: ox-hugoが認識せず、front matterに一切出てこない
:EXPORT_HUGO_COVER: custom/foo.jpg

;; OK: 唯一の任意キー用の経路
:EXPORT_HUGO_CUSTOM_FRONT_MATTER: :cover "custom/foo.jpg"
\end{verbatim}

Emacsのcaptureテンプレート側も同じ間違いをしていたので、新規記事作成時に自動挿入
される空のプレースホルダーも \texttt{:cover ""} の形に直した。

\subsection{{\bfseries\sffamily DONE} Blowfish（Hugoテーマ）のショートコード使い方まとめ}
\label{sec:orgb8fda35}
参照元は \href{https://github.com/nunocoracao/blowfish}{nunocoracao/blowfish} の exampleSite ドキュメントと \href{https://blowfish.page/docs/shortcodes/}{公式サイトのshortcodesページ}（2026年7月確認）。

ox-hugoでタングル/エクスポートする前提なので、ショートコードを書く部分は全部 \texttt{\#+begin\_export hugo} 〜 \texttt{\#+end\_export} で囲んである。org地の文（説明・表）はそのままMarkdownとして出力されるので、export ブロックは不要。

org-mode的には「構文そのものを文字として見せたいexportブロック」と「実際にHugoに変換させて機能させるexportブロック」は区別が必要である。 \texttt{\#+begin\_export hugo} はox-hugoに素通しされて実際にレンダリングされてしまうので、構文自体を文字として見せたい場合は \texttt{\#+begin\_example=（または =\#+begin\_src org=）で一段リテラル化してから、その直後に本物の =\#+begin\_export hugo} ブロックを続ける、という2段構成にしている。

ただし \texttt{\#+begin\_example} で囲んだだけでは不十分だった。Hugoのショートコード展開は、囲んでいるのがMarkdownのコードフェンスかどうかを見ずに、ファイル全体のテキストから波括弧2つのショートコード記法を機械的に探して実行してしまうため、コードブロックの中に書いた例文もそのまま実行されてビルドエラーや取得失敗の原因になる。これを防ぐには、Hugo公式のショートコードのエスケープ記法を使う必要がある。開き括弧の直後と閉じ括弧の直前に「/* 」「 */」を挟むと、実行されずに文字通りの文字列としてそのまま出力される。以下すべての節の「書き方はこう」の例では、この記法で統一した。
\subsubsection{Alert（警告・注意喚起ボックス）}
\label{sec:orga7f6a7a}

記事内に目立つメッセージボックスを表示する。中身は Markdown 記法。

書き方はこうなる。

\begin{verbatim}
#+begin_export hugo
{{</* alert */>}}
**Warning!** This action is destructive!
{{</* /alert */>}}
#+end_export
\end{verbatim}

実際にレンダリングすると、こう表示される。

アイコン付き・色指定もできる。

\begin{verbatim}
#+begin_export hugo
{{</* alert icon="fire" cardColor="#e63946" iconColor="#1d3557" textColor="#f1faee" */>}}
This is an error!
{{</* /alert */>}}
#+end_export
\end{verbatim}

\begin{center}
\begin{tabular}{ll}
パラメータ & 説明\\
\hline
icon & 任意。左側アイコン名。デフォルト: triangle-exclamation\\
iconColor & 任意。アイコン色（hex or カラー名）\\
cardColor & 任意。カード背景色\\
textColor & 任意。テキスト色\\
\end{tabular}
\end{center}

\label{sec:org7cf7b74}

\subsubsection{Button}
\label{sec:org3e095f1}

書き方はこう。 \texttt{pageRef} は存在する内部ページのパスを指定する必要があるので、ここでは記法例として \texttt{docs/getting-started} を挙げているが、実際に使う際はサイト内の実在パスに置き換えること（存在しないパスを \texttt{pageRef} に渡すとビルド時に \texttt{REF\_NOT\_FOUND} エラーになりビルド自体が止まる）。

\begin{verbatim}
#+begin_export hugo
{{</* button href="#button" target="_self" */>}}
Call to action

{{</* button pageRef="docs/getting-started" */>}}
Get started
{{</* /button */>}}
#+end_export
\end{verbatim}

\texttt{href} 版（任意URL/アンカー）はそのままレンダリングできる。

\subsubsection{補足（org運用時の注意点）}
\label{sec:org15f2605}

\texttt{\#+begin\_export hugo ... \#+end\_export} の中身は ox-hugo によって \textbf{無変換のまま素通し} される。org内の \texttt{*bold*} や \texttt{/italic/} のようなorg記法は効かないので、ショートコード内で強調したい場合はMarkdownの \texttt{**bold**} / \texttt{*italic*} をそのまま書く（この記事もその方針で統一している）。

\texttt{all-posts.org} のようにファイル内に複数記事が \texttt{* 見出し} で区切られている場合、ox-hugoの \texttt{\#+hugo\_base\_dir} や各見出しの \texttt{:EXPORT\_FILE\_NAME:} プロパティ設定が別途必要になる。

既存記事に貼り付ける際は、export blockの直前直後に空行を入れないとorg側のパース崩れが起きるケースがあるので注意する。

Admonitionだけはショートコードではなく \texttt{render-blockquote.html} によるMarkdown render hook実装である。

「構文そのものを文字として見せたい」場合は、=\#+begin\_export hugo= をそのまま書くのではなく \texttt{\#+begin\_example} （または \texttt{\#+begin\_src org} ）で一段リテラル化してから、その直後に本物の \texttt{\#+begin\_export hugo} ブロックを続けて実際のレンダリング結果も見せる、という2段構成にしておくと分かりやすい。

ただし \texttt{\#+begin\_example} で囲むだけでは足りない。Hugoのショートコード展開はMarkdownのコードフェンスの中かどうかを見ずに、ファイル全体から波括弧2つのショートコード記法を探して実行してしまうため、例文として書いたつもりの \texttt{pageRef} や外部URL指定がそのまま実行されて \texttt{REF\_NOT\_FOUND} やfetch失敗の原因になることがある。=\#+begin\_example= の中に書くショートコード例は、開き括弧の直後と閉じ括弧の直前に「/* 」「 */」を挟むエスケープ記法（Hugo公式）で書いておく必要がある。
\subsection{{\bfseries\sffamily DONE} 画像消失を直しに行ったら、直すべき場所が4つあった話}
\label{sec:org9e1a272}
前回、3ヶ月半前から全記事の画像が消えていたことに気づいた話を書いた。
原因は分かったので「あとは直すだけ」のつもりだったのだが、実際に手を
付けてみると、直すべき場所は1箇所どころか4箇所あった。しかも直している
最中に、また別の画像を消すというオチまで付いた。備忘として一通り
記録しておく。
\subsubsection{そもそもの根本原因：flatファイルとPage Bundleの取り違え}
\label{sec:org32dd25d}

うちのHugoサイトは、ox-hugoが記事を \texttt{content/post/<slug>.md} という
flatなファイルとして書き出す構成になっていた。カバー画像は
\texttt{content/post/<slug>/cover.jpg} という、記事ファイルと同名の別
ディレクトリに \texttt{deploy.sh} が機械的に配置する、という運用でずっと
やってきた。

これがそもそもの間違いだった。Hugoの世界では \texttt{<slug>.md} と \texttt{<slug>/}
は同名でも無関係な存在で、後者はPage Resourceとして認識されない。
Blowfishテーマのカバー画像自動検出（ \texttt{.Resources.ByType "image"} ）は
Page Bundle（ \texttt{<slug>/index.md} の形）でしか機能しないので、うちの
構成では最初から蚊帳の外だった。 \texttt{deploy.sh} が季節画像をローテー
ションで機械的に置き続けていたのは、いわばこの構造的な欠陥を隠す
ための対症療法だったわけだ。
\subsubsection{直した場所その1：all-posts.org を一括変換}
\label{sec:orgf2f460d}

ox-hugoには \texttt{:EXPORT\_HUGO\_BUNDLE:} という、まさにこのためのプロパティ
がある。全49記事の \texttt{:EXPORT\_FILE\_NAME: <slug>} を

\begin{verbatim}
:EXPORT_HUGO_BUNDLE: <slug>
:EXPORT_FILE_NAME: index
\end{verbatim}

に機械的に変換した。Hugoは \texttt{<slug>.md} でも \texttt{<slug>/index.md} でも
同じ \texttt{/post/<slug>/} に解決するので、パーマリンクへの影響はゼロ。
これは気楽に一括変換していい変更だった。
\subsubsection{直した場所その2： \texttt{deploy.sh} のカバー画像配置ロジック}
\label{sec:org6062ea2}

ここで最初の見落としに気づいた。カバー画像を置く \texttt{place\_covers()}
関数は \texttt{content/post/*.md} を直接グロブしていたので、記事が
\texttt{<slug>/index.md} に変わった瞬間、対象ファイルを1件も見つけられなく
なって沈黙する。グロブを \texttt{*/index.md} に変え、post\_dirの導出も
文字列結合からindex.mdの親ディレクトリ参照に直した。
\subsubsection{直した場所その3と4：新規記事が古い形式に戻ってしまう2つの入り口}
\label{sec:orgb5254a4}

ここまでで「よし直った」と思っていたのだが、もう2箇所あることに
気づいた。新規記事は \texttt{C-c c b} のorg-captureテンプレートから作る
のだが、Emacs設定（ \texttt{orgx-core.el} のベース版と、それを上書きする
\texttt{personal/ac1965.el} の2箇所）の両方とも \texttt{:EXPORT\_FILE\_NAME:
\%(org-id-new)} のままだった。これでは次に書く記事から、また
flat構造に逆戻りしてしまう。

さらにもう1つ。 \texttt{all-posts.org} の冒頭には、ネタをAIに投げて記事の
下書きを生成させるためのプロンプトテンプレートを仕込んであるの
だが、その中のPROPERTIESドロワーの見本も \texttt{EXPORT\_FILE\_NAME: <slug>}
のままだった。ソースコードだけ直して、その生成元になるテンプレート
文章を見落とすところだった。地味だが、これを見落とすと「なぜか
たまに古い形式の記事が紛れ込む」という原因不明のバグを将来の自分に
仕込むところだった。
\subsubsection{そして、また画像を消した}
\label{sec:org3dec7d2}

一通り直したので、動作確認のつもりで一度 \texttt{content/post} を
\texttt{rm -rf} してから再exportしてみた。 \texttt{content/post} はビルド成果物
なので.gitignore対象、消しても再生成されるだけのはずだった。

ところが、記事本文で使っていたBlowfishのfigure/carouselショートコード
（ \texttt{src}"frieren.jpg"= や \texttt{images}"inuyama-fest/*"= のように画像を
直接指定するタイプ）が参照していた画像だけは戻ってこなかった。

理由は単純で、これらはPage Resourceとして \texttt{content/post/<slug>/}
直下に \textbf{手で置いていただけ} のファイルだった。カバー画像は
\texttt{deploy.sh} が毎回決定的に再生成するし、Orgの \texttt{[[file:...]]} リンク
はox-hugoが自動でコピーし直してくれる。しかしshortcode内の
\texttt{src}"\ldots{}"= はox-hugoにとってただの文字列で、どの自動生成の仕組みにも
紐づいていなかった。一番安全なはずの「ビルド成果物だから消していい」
という前提が、実はこの種の画像には最初から成り立っていなかった、
というわけだ。
\subsubsection{deployブランチという名の保険}
\label{sec:org4fead5c}

さすがに焦ったが、幸い逃げ道が残っていた。うちの \texttt{deploy.sh} は
ビルド後の \texttt{public/} を、sourceとは別の \texttt{deploy} ブランチにpushして
いる。つまり、公開されているHTML・画像そのものが独立したGit履歴を
持っているということだ。

GitHubのTrees APIで \texttt{deploy} ブランチの履歴を遡り、3月21日の大量
削除が起きる直前、最後に正常だったdeployコミットを特定した。そこから
Hugoのリサイズキャッシュ（ \texttt{*\_hu\_<hash>.*} ）を除いた \textbf{オリジナル
ファイルだけ} を掘り出したところ、10記事・37ファイル、 \texttt{frieren.jpg}
も \texttt{inuyama-fest/} の写真11枚も無事に発見できた。全ファイル、コミット
時点のGit blobサイズと突き合わせて一致を確認済みで、EXIF情報から
撮影日時まで読み取れる、正真正銘のオリジナルだった。

これを機に、 \texttt{assets/img/post-assets/<slug>/} という「正本置き場」を
新設し、 \texttt{deploy.sh} に \texttt{sync\_post\_assets()} を追加した。build毎に
ここから \texttt{content/post/<slug>/} へ同期するので、以後は \texttt{rm -rf
content/post} してもこの種の画像はもう消えない。

\subsection{{\bfseries\sffamily DONE} Makefile が自分自身を tangle する設定で、実機でしかハマらないバグを4連発踏んだ話}
\label{sec:org723a813}
前回、 \texttt{README.org} の Makefile ブロックでタブが壊れる話を書いたけど、あの後も
続きがあった。実際に手元で \texttt{make reload} や \texttt{make diagrams} を叩くたびに、
サンドボックス環境の検証だけでは踏めない類のバグが次々出てきて、結局4段階の
実機デバッグになった。せっかくなので記録として残しておく。

\textbf{最初の直しが別のバグを生んだ}

タブが \texttt{org-babel-tangle} に飲み込まれる問題、最初は \texttt{.RECIPEPREFIX :} >= で
recipe行の先頭マーカーをタブ以外の文字に変える案で直したつもりだった。だがこれは
GNU Make 3.82以降の機能で、macOS標準の \texttt{/usr/bin/make} はGPLv3回避のため3.81に
凍結されている。案の定、手元で試してもらったら:

\begin{verbatim}
Makefile:87: *** missing separator.  Stop.
\end{verbatim}

同じエラーが別の行で再発した。バージョン依存の機能に頼ったのが失敗で、結局
本物のタブ文字に戻し、 \texttt{org-src-preserve-indentation} を \texttt{t} にして tangle時の
インデント除去処理自体を無効化する方式に変更した。

\textbf{その修正がまた別のファイルを壊した}

ところがこの \texttt{org-src-preserve-indentation} を \texttt{(setq ...)} で \textbf{グローバルに}
設定したのが次の落とし穴だった。README.org は1回のEmacsセッションで全ブロックを
tangleするので、Makefileだけでなく \texttt{early-init.el} や \texttt{lisp/*.el} 全部に
この設定が波及してしまい、org側の見た目そろえ用スペースが \texttt{early-init.el} の
1行目（ \texttt{lexical-binding} cookie）にまで残ってしまった。結果、Emacs起動時に
こんな警告が出た。

\begin{quote}
Warning (files): Missing 'lexical-binding' cookie in "\textasciitilde{}/.emacs.d-stable/early-init.el".
\end{quote}

直し方は2段階tangleにすること。1段階目は普通に（indentation preserveなし）
全ブロックをtangleして \texttt{early-init.el} 等を正しく生成し、2段階目で
\texttt{org-babel-tangle-file} の言語フィルタ引数に \texttt{\textbackslash{}"makefile\textbackslash{}"} だけを渡して、
Makefileブロックだけを preserve-indentation=t で再tangleする。これで両方
正しくなった。

\textbf{leafマクロが理由不明のまま原因不特定になった件}

Makefile周りが片付いたところで、今度は実際の起動ログから \texttt{ui-which-key}
モジュールが読み込み失敗しているのが見つかった。

\begin{verbatim}
[modules] Failed to load ui-which-key: Symbol's value as variable is void: which-key
\end{verbatim}

該当箇所は \texttt{leaf which-key} を \texttt{:straight} と \texttt{:if} の組み合わせで
Emacs 30以降／未満に条件分岐させていた部分。手元にEmacs 30系が無かったので、
straight・leaf・leaf-keywordsを実際にブートストラップして単体評価まで試したが、
正直なところ \texttt{leaf-keywords.el} の \texttt{:straight} 拡張内部の正確な原因までは
特定しきれなかった。原因究明より実利を取って、 \texttt{leaf} マクロを経由せず
素の \texttt{(when (< emacs-major-version 30) (straight-use-package 'which-key))}
に書き換えることで問題自体を回避した。

\textbf{Puppeteerのバージョン固定にも足をすくわれた}

図版のMermaidレンダリング（ \texttt{mmdc} ）でも似たようなことが起きた。エラーメッセージは
素直に「Chromeが見つからない」と言っていて、Puppeteer公式の案内通り
\texttt{npx puppeteer browsers install chrome-headless-shell} を勧めたのだが、これが
外れだった。 \texttt{mmdc} が同梱する \texttt{puppeteer-core} は特定バージョンのChromeに
ピン留めされているため、システムに最新版を入れても一致せず、同じエラーが
再発し続けた。

\textbf{結局16枚全部揃った}

最終的に \texttt{dot-tangle} / \texttt{dot-svg} / \texttt{mmd-tangle} / \texttt{mmd-svg} を1つにまとめた
\texttt{make diagrams} で、design\_spec.org側13枚 ＋ README.org側3枚の計16枚が
問題なくレンダリングされるところまで確認できた。

サンドボックスでの検証だけでは絶対に踏めないバグ（Makeのバージョン差、
tangleの副作用範囲、leafマクロの内部実装、puppeteerのバージョン固定）が
4段階連続で出てきて、そのたびに「サンドボックスでは動いたのに」という
展開になった。実機で試してもらうまで確信が持てない類の不具合が、こんなに
積み重なるとは思っていなかった
